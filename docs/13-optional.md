# 13. Параноидальные слои (`optional/`)

> Модули 3, 5, 6, 8 промпта — то, что дорого в удобстве, требует дополнительного
> оборудования или увеличивает доверенную базу. Базовый слой их не включает; каждый
> модуль включается отдельно, после установки, и выключается обратно.

```sh
doas /root/vh/optional/status                    # что включено
doas /root/vh/optional/<модуль>/enable           # включить (скрипт объясняет и спрашивает)
doas /root/vh/optional/<модуль>/disable          # выключить
```

Все команды — **[ПОСЛЕ ЗАГРУЗКИ]**, от админа на tty2. Модули идемпотентны: повторный
`enable` ничего не ломает. Перед изменениями в PAM, загрузке или USB держите открытым
второй root-шелл (`doas -s` на другом TTY) — им вы исправите ошибку, если войти заново
не получится.

## strict-net

**Угроза.** В базовом слое у повседневного пользователя и админа есть сеть: вредонос с
их правами связывается с атакующим напрямую. Даже без сети остаётся канал через DNS:
запрос `секрет.атакующий.tld` к локальному unbound тот честно перешлёт апстриму, а
ответ (TXT) вернёт — это полноценный двусторонний канал.

**Как устроено.** Правила для людей и для DNS на loopback вынесены из
`/etc/nftables.conf` в подключаемые файлы `/etc/vh/nft/people.nft` и `lo-dns.nft`
(`include` внутри цепочки). Модуль подменяет их строгими:

```
# people.nft (строгий)
meta skuid "root" ip daddr @root_https tcp dport 443 accept   # root: только зеркала xbps и только на время
meta skuid @people_tmp accept                                # временное разрешение (vh-net allow)
# lo-dns.nft (строгий)
meta skuid "browser" ... th dport 53 accept                  # браузеру DNS нужен
meta skuid "chrony"  ... th dport 53 accept                  # имена NTS-серверов
meta skuid @dns_tmp  ... th dport 53 accept                  # временно
```

**Временные разрешения без изменения правил.** Принцип промпта: правила и цепочки в
рантайме не меняются никем. Меняются только **элементы** заранее объявленных
set'ов с флагом `timeout` — ядро само удаляет их по истечении срока, откат не зависит
от демона:

```sh
doas vh-net allow admin 10      # админу сеть и DNS на 10 минут
doas vh-net xbps 30             # root: DNS и HTTPS к адресам зеркал на 30 минут (vh-update делает сам)
doas vh-net status
nft list set inet vh people_tmp # руками: то же самое
nft add element inet vh people_tmp '{ 1000 timeout 10m }'
```

**Проверка.** От пользователя: `getent hosts voidlinux.org` → ошибка; у админа
`doas nft list chain inet vh drop_log` — растёт счётчик. Браузер работает.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Утечки по сети и DNS от процессов людей | Ввод в окно браузера через Wayland (у процессов пользователя есть основной сокет); каталог загрузок | нет | git/ssh/pip — только через `vh-net allow` |

## dns-pin

**Угроза.** unbound проверяет сертификат DoT-сервера, chrony — NTS-KE. Но «проверяет» —
по системному хранилищу из ~150 корневых УЦ: сертификат на `dns.quad9.net`, выпущенный
любым из них (по ошибке, по принуждению, взломом), принимается.

**Как устроено.** Пин — файл только с корнями УЦ выбранных провайдеров. Корень берётся
из **проверенной** цепочки реального подключения (python `ssl`, `get_verified_chain()`).
Подключение делается **от имени самого сервиса** (`setpriv --reuid=_unbound`): файрвол
разрешает `_unbound` только 853 к адресам апстримов, ослаблять его не нужно. Затем:

```
unbound.conf:  tls-cert-bundle: "/etc/unbound/ca-pin.pem"
chrony.conf:   ntstrustedcerts /etc/chrony/nts-pin.pem
               nosystemcert
```

Пиним **корень**, а не сертификат сервера: провайдер меняет промежуточные и конечные
сертификаты часто, корень — редко. Провайдеры по умолчанию (Quad9, Mullvad) — с
разными УЦ: смена у одного не оставит без DNS.

**Сверка по второму каналу обязательна.** Если подключение при `enable` уже
перехвачено, вы запиньте УЦ атакующего. Отпечатки SHA256 корней скрипт печатает —
сравните их с другого устройства и другой сети (браузер → сертификат сайта
провайдера → корень; или crt.sh).

**Отказ закрытый.** Провайдер сменил УЦ → DNS (или время) перестают работать. Это
правильно. Исправление — повторный `enable` со сверкой. Временно выключать проверку
сертификатов запрещено ([09](09-updates.md)).

**Проверка отказа.** Впишите в `forward-addr` чужое имя после `#` (например,
`9.9.9.9@853#example.com`), `sv restart unbound`, `getent hosts voidlinux.org` — ошибка.
Верните.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| MITM DoT и NTS сертификатом постороннего УЦ | Компрометация самого выбранного УЦ или провайдера | нет | ручное обновление пина при смене УЦ |

## usb-auth

**Угроза — BadUSB.** Устройство, которое выглядит флешкой, объявляет и клавиатурный
интерфейс и печатает команды. Ядро привязывает драйвер клавиатуры раньше, чем любое
правило udev успеет среагировать: клавиатурный ввод попадает в активный TTY — например,
в root-шелл админа. Подделать VID:PID и серийный номер «своего» устройства легко.

**Как устроено (три механизма ядра).**

1. `usbcore.authorized_default=2` в cmdline: устройства на **внутренних** портах
   (`connect_type=hardwired` по таблицам ACPI — встроенная камера, Bluetooth) авторизуются
   сами, на внешних — нет. Неавторизованное устройство перечисляется (видны дескрипторы),
   но не конфигурируется: драйверы к нему не привязываются.
2. `interface_authorized_default=0` у корневых хабов: даже авторизованное устройство
   получает интерфейсы **неавторизованными**. Каждый интерфейс разрешается отдельно.
3. Помощник `vh-usb-udev` (вызывается udev) решает, что разрешить:
   - интерфейсы внутренних устройств — да (кроме камеры при `VH_CAMERA=no` и Bluetooth при
     `VH_BLUETOOTH=off`);
   - свой FIDO2-ключ (`/etc/vh/usb-keys.conf`: точный порт + VID:PID + serial + **ровно один
     интерфейс HID без boot-протокола клавиатуры**) — да;
   - устройство, подключённое командой `vh-usb attach`, — **только интерфейсы класса 08**
     (накопитель); HID этой «флешки» остаётся мёртвым.

```sh
doas vh-usb list                 # внешние устройства и authorized=0/1
doas vh-usb attach               # Super+U: авторизовать накопитель, смонтировать vfat/exfat в /media/user
doas vh-usb detach               # Super+Shift+U: sync, umount, деавторизовать
doas vh-usb-allow-key            # (админ) внести свой FIDO2-ключ
# руками — то же самое через sysfs:
cat /sys/bus/usb/devices/*/port/connect_type
echo 0 > /sys/bus/usb/devices/usb1/interface_authorized_default
echo 1 > /sys/bus/usb/devices/1-2/authorized
echo 1 > /sys/bus/usb/devices/1-2:1.0/authorized       # только интерфейс накопителя
```

Флешка монтируется с `nodev,nosuid,noexec,nosymfollow` и UID пользователя. ФС флешки
всё равно разбирает ядро (vfat/exfat) — это остаточный риск: враждебная ФС — путь к
уязвимости драйвера. Носители с ключом подписи и бэкапами подключает только админ.

**Ошибка ACPI.** Если физически внешний порт помечен `hardwired`, ядро ему доверяет.
`enable` показывает `connect_type` всех портов — сверьте с разъёмами. Обход: правило udev
с `ATTR{authorized}="0"` по пути этого порта.

**Встроенная клавиатура.** На MSI GF63 она на i8042 (PS/2), правила USB её не касаются.
На ноутбуках с клавиатурой на внутреннем USB её порт должен быть `hardwired` (проба
покажет), иначе она перестанет работать — даже для пароля LUKS: `authorized_default=2`
действует и в initramfs.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| BadUSB-клавиатуры и сетевые карты, DMA через USB-устройства без авторизации | Разбор ФС флешки ядром; клон своего FIDO-ключа в том же порту; ошибка ACPI | нет | USB-мышь/клавиатура снаружи не работают; флешки — Super+U |

## fido2

**Угроза.** Пароль подсмотрели, записали кейлоггером или вытащили фишингом. Второй
фактор — то, что нельзя скопировать удалённо: ключ FIDO2.

**Как устроено.** `pam_u2f` в стеках `system-login`, `doas`, `swaylock` в режиме
**required** — пароль *и* ключ. `sufficient` запрещён: тогда ключ заменял бы пароль.

```
auth  required                pam_faillock.so preauth
auth  [success=1 default=bad] pam_unix.so try_first_pass
auth  [default=die]           pam_faillock.so authfail
auth  [success=1 default=bad] pam_u2f.so authfile=/etc/u2f_mappings cue origin=pam://void-hardened appid=pam://void-hardened pinverification=1
auth  [default=die]           pam_faillock.so authfail
auth  required                pam_permit.so
```

Разбор управляющих флагов: `[success=1 default=bad]` — успех пропускает следующую
строку (счётчик ошибок), неудача помечает стек проваленным и идёт к `authfail`, который
учитывает попытку и завершает стек (`die`). Так ошибка любого фактора считается
faillock'ом.

- **PIN** (`pinverification=1`) для входа и doas: ключ, украденный вместе с ноутбуком,
  без PIN бесполезен. Для swaylock — только касание: частая разблокировка быстрая, а
  пароль всё равно нужен.
- `authfile=/etc/u2f_mappings` (root, 0644), а не файл в $HOME: его пишет сам
  пользователь. `nouserok` запрещён — иначе пользователь без записи входит без ключа.
- Доступ к ключу без elogind: тег `uaccess` не работает, поэтому udev-правило отдаёт
  hidraw **только своих ключей** (VID:PID + serial) группе `fido`. Это не группа `input`:
  она не даёт чтения клавиатур.
- **Два ключа** на человека — основной и запасной, храните отдельно. Потеря
  единственного ключа = вход только через live-флешку.
- YubiKey: выключите OTP-интерфейс (он печатает как клавиатура):
  `ykman config usb --disable OTP`.

**Если не войти.** Live-флешка → открыть LUKS → chroot → `cp /etc/pam.d/system-login.vh-orig /etc/pam.d/system-login`.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Украденного пароля; ключа без PIN | libfido2 и pam_u2f разбирают ответы HID в root-процессах (поддельный ключ — поверхность атаки); ключ, оставленный в ноутбуке, при swaylock — один фактор из двух | нет | касание при разблокировке, PIN при входе и doas, 2 ключа |

## sb-offline-keys

**Угроза.** В базовом слое приватный ключ db лежит в `/var/lib/sbctl/keys`. Root-руткит
подпишет им свою UKI — Secure Boot её пропустит, и руткит переживёт переустановку
пакетов. Хуже: даже с ключом офлайн руткит может подменить то, **из чего** собирается UKI
(модуль dracut, cmdline, хук `kernel.d`), — и при следующем обновлении вы сами подпишете
его образ.

**Как устроено.**

1. Ключи PK/KEK/db переносятся на отдельную флешку с LUKS2 + XFS. На корневой ФС их
   больше нет. `vh-keys mount` открывает носитель и монтирует ключи в
   `/var/lib/sbctl/keys` **и выключает сеть** (rfkill, eth0 down) на время подписи;
   `vh-keys umount` всё возвращает.
2. `vh-limine-update` при `KEYS_OFFLINE=yes` без носителя **падает с ошибкой**, а не
   оставляет неподписанную UKI; при включённом Secure Boot — тоже. Удаление старых UKI —
   только после успешной подписи: сбой оставляет ESP в рабочем состоянии.
3. Перед подписью — `vh-uki-verify` с эталонами **на носителе ключа**:
   - `xbps-pkgdb` для пакетов, из которых собирается UKI;
   - хэши файлов не из пакетов (`/etc/dracut.conf.d`, `/etc/default/dracut-uefi-hook`,
     `/etc/kernel.d`, свои модули dracut, `vh-limine-update`…);
   - секция `.cmdline` новой UKI побайтно, `.uname` — с версией пакета (разбор PE на
     python `struct`, без binutils);
   - содержимое initramfs (`.initrd`: ранний cpio с микрокодом + сжатый основной) — с
     прошлой одобренной UKI: новые, удалённые и изменённые файлы показываются, админ
     подтверждает.
4. `vh-update` в этом режиме: пакеты скачиваются с сетью (`xbps-install -uD`), затем
   «вставьте носитель», установка и подпись — без сети, носитель отключается, сеть
   возвращается.

**Порядок включения.** Сразу после установки, до первого сеанса пользователя и запуска
браузера: эталоны снимаются с текущего состояния. Подменённое к этому моменту станет
«эталоном».

**Остаточный риск.** Удалённые с корня файлы ключей могли остаться в свободных блоках
(том зашифрован, но root работающей системы читает его целиком). Для полной гарантии —
перевыпуск ключей прямо на носителе: Setup Mode в BIOS → `vh-keys mount` →
`sbctl create-keys` (в смонтированный каталог) → `sbctl enroll-keys` → переподпись UKI.
Руткит, перехвативший саму проверку или sbctl, её обойдёт — полностью закрывает только
**параноидальный вариант**: сборка и подпись UKI из проверенной live-флешки в chroot
(`xbps-pkgdb -r /mnt -a`, сверка с офлайн-снимком, `xbps-reconfigure -f linux6.18`).

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Подписи чужой UKI украденным ключом; подмены входных данных сборки | Руткит, обманывающий саму проверку; копии ключей в свободных блоках | нет | обновление ядра/микрокода — с носителем и без сети; носитель нужно беречь и дублировать |

## tpm2-totp

**Угроза — evil maid.** Пока ноутбук без присмотра, атакующий подменяет загрузку
(или ставит свою цепочку, загружаемую прошивкой) так, чтобы она выглядела как ваша и
спросила пароль LUKS. Secure Boot это затрудняет, но не исключает (уязвимость прошивки,
сброшенный пароль BIOS, ключ db).

**Как устроено.** Секрет TOTP запечатан в TPM на значения PCR. TPM отдаёт его, только
если PCR совпадают с теми, что были при запечатывании, — то есть загрузилось то же
самое. initramfs показывает 6 цифр **до** запроса пароля, вы сверяете с телефоном. Не
совпало — пароль не вводите.

| PCR | Что ловит |
|---|---|
| 0, 2 | код прошивки и Option ROM (откат/подмена прошивки) |
| 4 | хэши загруженных EFI-образов: Limine и **сама UKI**. UKI, подписанная украденным ключом db, проходит Secure Boot (PCR 7 не меняется), но её хэш другой — PCR 4 это ловит |
| 7 | состояние Secure Boot и ключи (PK/KEK/db/dbx) |
| 14 | ноль до показа кода; после — расширяется случайным значением |

**Почему не PCR 8 и 9 и откуда PCR 14.** Промпт предлагал расширять PCR 8. Но Limine 12
при Secure Boot с вписанным хэшем конфига **сам** пишет в PCR 8 (cmdline и пути) и PCR 9
(конфиг и файлы) — PCR 8 в initramfs не нулевой, а PCR 9 меняется с каждой UKI. Свободный
PCR 14 решает ту же задачу: секрет запечатан на PCR14 = 0, initramfs после показа кода
(и на аварийных путях) расширяет его — **работающая система больше не вычислит код**, ни
сейчас, ни на будущее время. Без этого root работающей системы мог бы заранее посчитать
коды для поддельной цепочки.

**Генерация и перезапечатывание — только в initramfs** (из работающей системы PCR 14
уже расширен). Флаг на корневой ФС — только факт наличия файла:

- `enable` ставит `/var/lib/vh/totp-generate` → при загрузке, после пароля LUKS: пароль
  восстановления (diceware ≥ 5 слов), QR-код для телефона;
- `vh-limine-update` при новой UKI ставит `/var/lib/vh/totp-reseal` → при загрузке код один
  раз не совпадёт (это ожидаемо), initramfs покажет `/proc/version` — сверьте с версией,
  которую `vh-update` велел записать, — и попросит ввести `RESEAL` и пароль восстановления.
  **Неожиданный запрос перезапечатывания — признак подмены.**

**Защита секрета в TPM.** С паролем восстановления секрет извлекается целиком
(`tpm2-totp recover`). При пустой lockout-авторизации root сбрасывает счётчик защиты от
перебора и подбирает пароль без ограничений. Поэтому `enable` задаёт случайную
lockout-авторизацию (`tpm2_changeauth -c lockout`) и `tpm2_dictionarylockout`: 5 попыток,
сутки блокировки. Значение запишите офлайн вместе с ключами Secure Boot.

**Подмена часов.** Время в TPM не измеряется: со сброшенным паролем BIOS атакующий
переводит RTC вперёд, загружает подлинную цепочку, записывает код и подкладывает
поддельную, которая покажет его в нужную минуту. Защита — пароль администратора BIOS и
(если прошивка умеет) смена даты только под ним. Иначе — остаточный риск.

**fTPM (Intel PTT) живёт внутри ME:** доверие к tpm2-totp = доверие к ME.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Подмены прошивки, загрузчика, UKI, настроек SB до ввода пароля | Окно перезапечатывания (TOFU); подмена часов без пароля BIOS; ME | ~0,3 с на вычисление кода | сверка кода на каждой загрузке; RESEAL после обновлений |

## deadman

**Угроза — холодная загрузка.** Ключ тома LUKS и расшифрованные данные лежат в DRAM.
DRAM держит содержимое секунды—минуты после отключения питания (дольше, если охладить).
Атакующий, схвативший включённый ноутбук или выключенный только что, перезагружает
его со своей флешки (или переносит модули памяти) и читает ключ. `poweroff` здесь не
спасает: ядро не стирает память при выключении.

**Как устроено.** Резидентный root-демон `vh-deadman` (python stdlib) заранее делает
`mlockall`, открывает все дескрипторы и готовит буферы ioctl. По триггеру — без fork,
exec и чтения с диска:

1. `DM_DEV_SUSPEND` с `DM_NOFLUSH_FLAG | DM_SKIP_LOCKFS_FLAG` и `DM_TARGET_MSG "key wipe"`
   прямыми ioctl к `/dev/mapper/control` — ключ стёрт из памяти ядра за миллисекунды.
   Без этих флагов suspend заморозил бы XFS и сбросил грязные страницы — секунды под
   нагрузкой записи. После suspend читать с диска нельзя: page fault на вытесненную
   страницу — вечный D-state, поэтому всё загружено заранее;
2. `kill(-1, SIGKILL)` — память процессов освобождается и (при `init_on_free=1`) обнуляется;
3. `swapoff` и `reset` zram — zsmalloc не обнуляет освобождённые объекты сам;
4. `drop_caches=3` — page cache с расшифрованными файлами, dentry и inode (имена файлов);
5. MOR поддерживается: переменная NVRAM `VhPoweroff` и `sysrq b` — перезагрузка через
   прошивку, которая при POST стирает RAM; initramfs (модуль dracut `91vhdeadman`, самый
   ранний хук) видит переменную, удаляет её и выключает машину. Без MOR — `sysrq o`.

Триггеры:

- **тревожный:** извлечение метки — любого USB-устройства на шнурке (событие `remove` из
  NETLINK_KOBJECT_UEVENT, проверка, что отправитель — ядро); тревожная комбинация
  Правый Ctrl + Правый Alt + End на встроенной клавиатуре (evdev, работает и при
  зависшем mango). Данные последних секунд не сохраняются;
- **штатный:** любое выключение и перезагрузка проходят стадию 3 runit (сервисы
  остановлены, данные сброшены, корень только для чтения), последним шагом
  `shutdown.d/85-vh-deadman.sh` запускает тот же финал. Кнопка питания, крышка дольше
  K минут и простой дольше M минут (`vh-acpid`, раздел ниже) ведут сюда.

**Сторож простоя.** `enable` включает в `vh-acpid` блокировку через 15 и штатное
выключение через 60 минут без **физического** ввода — только встроенные клавиатура и
тачпад. idle-inhibit браузера (видео), USB-«дёргалка мыши» и uinput сеанс не продлевают.
Захватил устройство ввода (EVIOCGRAB) — демон не видит ввода и выключает машину: отказ
в безопасную сторону.

**Аппаратный сторож iTCO.** Если он есть и прошивка не заблокировала NO_REBOOT, демон
«гладит» `/dev/watchdog` (`nowayout=1`, 60 с). Гибель или зависание демона — сброс через
прошивку, MOR стирает RAM.

**Проверка на стенде** (промпт требует; `tests/vm`): маркерная строка в файле, в памяти
процесса и в недавно записанном файле → `vh-deadman final` → `dump-guest-memory` в
мониторе qemu → поиск мастер-ключа (`cryptsetup luksDump --dump-volume-key`) и маркеров.

**Остаточный риск.** Память процессов, застрявших в D-state на приостановленном томе;
грязные страницы недавно записанных файлов (без MOR — до потери питания); длинное
нажатие кнопки питания — аппаратное выключение мимо всего этого; TME (шифрования DRAM)
в Comet Lake нет.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Холодной загрузки после тревоги, выключения, простоя, крышки | D-state, грязные страницы, длинное нажатие кнопки, нет MOR | демон ~15 МБ RAM (mlockall), 0 пробуждений без сторожа | тревога теряет несохранённое; выключение по простою |

## session-netns

**Угроза.** Даже со строгим файрволом процессы сеанса видят сетевой стек ядра:
loopback-сервисы, DNS на 127.0.0.1, **абстрактные UNIX-сокеты** (привязаны к сетевому
namespace) — через них браузер и процессы пользователя могут найти друг друга и
передать дескриптор сетевого сокета.

**Как устроено.** agetty на tty1 запускает вместо `login` скрипт
`/usr/local/sbin/vh-login-netns` (параметр `--login-program` в `/etc/sv/agetty-tty1/conf`):

```sh
exec unshare --net -- sh -c 'ip link set lo up; sysctl -qw net.mptcp.enabled=0; exec login "$@"'
```

Весь сеанс — mango, терминалы, программы — живёт в пустом netns: только `lo`. Wayland,
PipeWire и D-Bus (zwifi управляет Wi-Fi через iwd) работают через сокеты **в ФС** и не
затронуты. Браузеру сеть нужна — root-лаунчер `vh-browser` уже делает
`nsenter --net=/proc/1/ns/net` (в базовом слое это ничего не меняет). sysctl `net.*`
действуют на netns: в новом — значения по умолчанию, поэтому MPTCP выключается заново.

**Проверка** из терминала сеанса: `ip -br link` → только `lo`; `getent hosts
voidlinux.org` → ошибка без единого пакета в сети init (счётчики nft не растут);
`Super+B` — браузер работает.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Сеть, DNS и абстрактные сокеты у процессов сеанса | Ввод в окно браузера через Wayland; каталог загрузок | нет | у программ пользователя нет сети совсем |

## session-apparmor

**Угроза.** Процесс пользователя (скомпрометированный терминал, плагин редактора)
против его же сеанса: IPC mango (`$XDG_RUNTIME_DIR/mango-PID.sock`) принимает
`dispatch spawn` и меняет привязки — можно снять «защищённую комбинацию»; сокет seatd —
открыть seat и получить ввод; user namespace — путь к уязвимостям ядра (nf_tables,
overlayfs) с CAP_NET_ADMIN в своём namespace.

**Как устроено.** Профиль `vh.mango` на `/usr/bin/mango` и дочерние:

- `panel` — netline и его меню (zpower, zrun…): им нужен IPC mango (теги, выход);
- `apps` — всё остальное, что запускает mango: `deny` на сокеты IPC mango и seatd,
  `deny userns`, `deny capability`, `deny network alg/packet`;
- переходы: `doas` и `vh-open` — `Ux` (свои root-лаунчеры с фиксированными аргументами;
  заглавная буква = окружение очищается, LD_PRELOAD не пройдёт), `unix_chkpwd` — в
  штатный профиль `unix-chkpwd` (без него swaylock не проверит пароль).

**Почему `abi <abi/4.0>`.** Медиация user namespace (`userns`) действует только для
профилей, объявивших ABI 4.0; со старым ABI `deny userns` молча не работает.

**Почему именованные переходы, а не профиль на путь.** Узкий профиль, прикреплённый к
`/usr/bin/doas`, применился бы и к doas админа на tty2; профиль с userns на
`/usr/bin/bwrap` позволил бы пользователю запустить bwrap со своими флагами
(`--unshare-net --cap-add`).

`enable` ставит профиль в режим **complain** (только журнал). Неделю поработайте,
проверьте отказы (`doas svlogtail kernel | grep vh.mango`) и включите
`enable --enforce`. Сеанс не стартует — войдите админом на tty2 и выполните `disable`.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Смены привязок mango, захвата seat, userns и AF_ALG у процессов сеанса | Основной сокет Wayland у процессов пользователя (virtual-keyboard в свои окна) | ~0 | `mmsg` из терминала не работает |

## viewers

**Угроза.** PDF, картинка или видео из интернета — данные, которые разбирает сложный
код на C (mupdf, libpng, ffmpeg). Эксплойт в нём получает права пользователя: файлы,
основной сокет Wayland (virtual-keyboard в терминал, screencopy, буфер обмена).

**Как устроено — `vh-open ФАЙЛ`** (python `-I`):

1. **Без гонки TOCTOU.** «Проверить путь, затем открыть» — две операции, между которыми
   браузер может подменить файл симлинком. Вместо этого компоненты пути проходятся через
   `openat(..., O_NOFOLLOW)` от корня, последний — `O_PATH|O_NOFOLLOW`, `fstat` — обычный
   файл. В bwrap передаётся **дескриптор** (`--ro-bind-fd`), путь больше не используется.
2. **Тип по сигнатуре** (а не по расширению): `%PDF` → zathura, PNG/JPEG/GIF/WebP → imv,
   MP4/MKV/WebM/Ogg/FLAC → mpv, текст → less (`LESSSECURE`).
3. **bwrap:** `--unshare-all` (нет сети), `--disable-userns`, `--cap-drop ALL`, `--clearenv`,
   свой `/proc` с `/dev/null` поверх `/proc/interrupts`, `/proc/softirqs`, `/proc/stat`
   (тайминги нажатий клавиш через счётчики прерываний), `/tmp` и `HOME` — каталоги на
   noexec-tmpfs хоста (noexec, пришедший из более привилегированного namespace, в userns
   не снимается), Wayland — только через фильтр `vh-wlfilter`, звук — ограниченный сокет
   PipeWire.
4. **seccomp** — фильтр из генератора `vh-seccomp` (python `struct`, это данные, а не
   сборка): `socket` только AF_UNIX, `clone` без CLONE_NEW*, `clone3` → ENOSYS (флаги в
   структуре BPF не видит, glibc откатится на clone), `personality` только 0, запрещены
   unshare/setns, монтирование, io_uring, bpf, perf_event_open, userfaultfd, keyctl,
   kexec, modify_ldt, ptrace. Первыми — проверка архитектуры и бита x32; всё прочее —
   безусловный ALLOW: ядро кэширует такие вызовы и BPF для них не запускает.
5. **PR_SET_MDWE** (W^X силами ядра) — для zathura, imv, less; не для mpv (Lua).

`vh-open --gpu` — свои видео с VA-API через render node (поверхность драйвера i915 —
только для своих файлов). PDF из интернета — сначала во встроенном pdf.js одноразового
профиля браузера.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Эксплойтов в просмотрщиках: нет сети, файлов пользователя, привилегированного Wayland | Уязвимость ядра, достижимая разрешёнными вызовами; тот же UID (выход из bwrap = права пользователя) | видео без GPU — CPU | открывать через `vh-open` |

## home-lockdown

**Угроза — закрепление.** Вредонос с правами пользователя создаёт `~/.bash_profile`
(login-bash прочитает его раньше `~/.profile`), `~/.local/share/applications/*.desktop`
с подменённым `Exec=`, `exec-once` в конфиге mango, `shell=` в foot, хуки git — и
переживает перезагрузку.

**Как устроено.** `$HOME` — `root:<группа> 0750`: пользователь не создаёт и не удаляет
файлы на верхнем уровне. Записываемы только `Documents Projects Pictures Videos Music
config-drafts .cache .local/state` (и `~/Downloads` → `/home/xfer`). Конфиги шелла, mango,
foot — root, только чтение. `~/.gnupg` — `root:<группа> 1770` (sticky): данные пишет
пользователь, а исполняемый конфиг (`pinentry-program` в gpg-agent.conf) — root.
`/etc/gitconfig`: `core.hooksPath` в пустой каталог, `core.fsmonitor=false` — чужой
репозиторий не исполнит свой код даже из приглашения шелла.

**Свои настройки.** Правьте копию в `~/config-drafts/.config/foot/foot.ini` и т. п.;
админ (после вашего выхода из сеанса) выполняет `doas vh-apply-config`: видит diff и
строки, которые запускают программы (`exec`, `spawn`, `shell=`, `script=`, `alias`…),
подтверждает каждый файл — он ставится владельцем root.

| Защищает от | Остаточный риск | Цена в скорости | Цена в удобстве |
|---|---|---|---|
| Закрепления через конфиги и автозапуск в $HOME | Программы, хранящие исполняемое в записываемых каталогах; python-скрипты пользователя (запуск руками) | нет | правка конфигов — через черновики и админа |

## Что осталось за рамками (следующий уровень)

- **Браузер в одноразовой виртуалке KVM** (qemu): изоляция на уровне гипервизора. Цена —
  ~1–2 ГБ RAM, нет аппаратного ускорения графики внутри (virtio-gpu без 3D — программный
  рендеринг), снять `kvm`/`kvm_intel` с блокировки и включить VT-x в BIOS — тогда эксплойт
  ядра хоста сможет поставить «тонкий гипервизор» под ОС.
- **Сеанс со своим фильтром seccomp на весь сеанс** (без NO_NEW_PRIVS, загрузчик от root в
  `vh-login-netns`) — промпт описывает; не реализован: каждый запрещённый вызов нужно
  проверить против PAM, doas и bwrap, а выигрыш поверх AppArmor-профиля сеанса мал.
- **Сборка и подпись UKI только из live-флешки** — описано в sb-offline-keys как ручная
  процедура.
