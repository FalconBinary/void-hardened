# 17. Инструменты системы на C

Свои программы системы — прокси Wayland, демоны крышки и стирания ключа, обновление
загрузчика, установка пакетов и другие — написаны на C (каталог [`src/`](../src)). До
коммита `a7665bd` они были на Python. Эта глава объясняет, зачем их переписали, что это дало
в цифрах, как они собираются и обновляются, как проверены и что изменилось в поведении.

## 1. Зачем

**Главное — безопасность, а не скорость.** Интерпретатор с FFI обходит `noexec`. Python
через `ctypes` выделяет память с правом исполнения и запускает в ней машинный код. Ему не
нужен ни исполняемый файл, ни `memfd`. Монтирование `/home` и `/tmp` с `noexec` от этого
не защищает ([05](05-system.md)). Пока системным инструментам нужен был `python3`, его
приходилось держать в системе. Теперь его нет совсем: xbps не ставит его даже как
зависимость (`ignorepkg=python3` в `/etc/xbps.d/20-vh-ignorepkg.conf`), а `vh-audit`
проверяет, что в системе нет ни интерпретаторов с FFI, ни компиляторов.

`apparmor` и `nftables` объявляют `python3` зависимостью, но только ради своих
Python-обвязок. `apparmor_parser`, `aa-status`, `aa-exec` и `nft` — программы на C, без
Python они работают. Не будут работать только `aa-logprof`, `aa-genprof` и
`aa-complain`/`aa-enforce`. Вместо двух последних: `apparmor_parser -r -C ПРОФИЛЬ` (режим
complain) и `apparmor_parser -r ПРОФИЛЬ` (режим из файла профиля).

**Память и процессор** — приятное дополнение. Цифры в разделе 3.

## 2. Что где

| Программа | Место в системе | Кто запускает | Что делает |
|---|---|---|---|
| `vh-wlfilter` | `/usr/local/bin` | сеанс (exec-once mango) | фильтрующий прокси Wayland для песочниц ([08](08-desktop.md)) |
| `vh-seccomp` | `/usr/local/libexec/vh` | `browser-sandbox`, `vh-audit` | фильтр seccomp-BPF для bwrap ([08](08-desktop.md)) |
| `vh-acpid` | `/usr/local/sbin` | runit | крышка, кнопка питания, простой ([05](05-system.md)) |
| `vh-limine-update` | `/usr/local/sbin` | хук ядра | подпись UKI, `limine.conf` с хэшами ([03](03-boot.md)) |
| `vh-pkg` | `/usr/local/sbin` | админ | установка программ с обезвреживанием ([12](12-daily.md)) |
| `vh-deep-clean` | `/usr/local/sbin` | админ | очистка системы с резервом и проверкой ([12](12-daily.md)) |
| `vh-deadman` | модуль deadman | runit, стадия 3 | стирание ключа LUKS ([13](13-optional.md)) |
| `vh-uki-verify` | модуль sb-offline-keys | `vh-limine-update` | проверка входных данных UKI ([13](13-optional.md)) |
| `vh-open` | модуль viewers | пользователь | просмотр файлов в песочнице ([13](13-optional.md)) |
| `vh-usb-udev` | модуль usb-auth | udev | решение об авторизации USB ([13](13-optional.md)) |
| `pin-fetch` | модуль dns-pin | `enable` | корень цепочки TLS для пиннинга ([13](13-optional.md)) |
| `vh-hashpw` | `/root/vh/tools` | только VM-стенд | хэш пароля yescrypt |

Общий код — `src/vh.c` (строки, файлы, конфиги `KEY=VALUE`, запуск программ без шелла),
`src/hash.c` (SHA-256 и BLAKE2b-512 без внешних библиотек), `src/seccomp.c` (генератор
фильтров, общий для `vh-seccomp` и `vh-open`). Внешняя библиотека есть только у `pin-fetch`
(OpenSSL — TLS) и `vh-hashpw` (libxcrypt).

Скрипты на `sh` (`vh-update`, `vh-audit`, `vh-suid-strip`, `vh-net`, `vh-usb`, модули)
остались на `sh`. Это «клей»: они вызывают xbps, `sv`, `nft`, и время уходит на сами эти
программы. Переписывать их на C нет смысла: быстрее не станет, а читать и проверять будет
труднее.

## 3. Замеры

Python-версия (коммит `a7665bd`) против C-версии, одинаковый вход. Машина — Apple M-серии
в родном arm64-контейнере Void. На i5-10500H обе версии медленнее примерно вдвое, а
соотношение то же. Замер прокси — `tests/c/bench_wlfilter.py`: 9 млн сообщений «кадр + ответ
композитора».

| Что | Python | C | Разница |
|---|---|---|---|
| `vh-wlfilter`: CPU на сообщение Wayland | 0,69 мкс | 0,017 мкс | ≈ 40× меньше |
| `vh-wlfilter`: память (VmRSS) | 11,4 МБ | 1,2 МБ | −10 МБ |
| `vh-acpid`: память (VmRSS) | 12,1 МБ | 1,4 МБ | −10,7 МБ |
| `vh-deadman`: память (оценка, закреплена `mlockall`) | ≈ 12 МБ | ≈ 1,5 МБ | −10 МБ, не уходит в zram |
| `vh-seccomp`: запуск (при каждом запуске браузера) | 14 мс | 0,23 мс | ≈ 60× быстрее |
| `vh-open`: запуск до `bwrap` | два запуска Python (сам и `vh-seccomp`) | < 1 мс | генератор seccomp встроен |
| Пакет `python3` на диске (`xbps-query -p installed_size`) | 23 МБ | — | убран из системы |
| Все 12 программ вместе (x86_64) | — | ≈ 0,6 МБ | |

**Как это выглядит на деле.** При прокрутке и видео браузер шлёт тысячи сообщений в секунду.
На Python это доли процента одного ядра, на C — сотые доли. Глазом разницу не увидеть
ни в задержке, ни в плавности: бюджет кадра при 60 Гц — 16,7 мс. Заметнее экономия памяти:
каждый резидентный процесс Python занимал 11–12 МБ, процесс на C — 1–1,5 МБ. С модулем
deadman это примерно −30 МБ в простое. Результаты `tools/vh-bench` и сравнение с CachyOS
([15](15-cachyos.md)) переписывание не меняет: скорость системы определяют ядро, Mesa,
Firefox и mango, а не эти программы.

## 4. Сборка

```sh
sh src/build.sh КАТАЛОГ        # собрать все программы (нужны gcc, openssl-devel, libxcrypt-devel)
```

В установленной системе **нет компилятора** — намеренно: вредонос с правами пользователя
не соберёт на месте свой инструмент (`vh-pkg` предупреждает о `gcc`, `clang`, `make`).
Поэтому программы собирает установщик — в RAM live-среды:

```sh
install/build-tools.sh /mnt          # ставит gcc в live (RAM), собирает, раскладывает в /mnt
```

`10-install.sh` вызывает его сам после копирования файлов. После перезагрузки live-среды
от компилятора не остаётся следа.

**Флаги защиты** (`src/build.sh`) — каждый закрывает свой класс эксплуатации ошибок памяти:

| Флаг | Что даёт |
|---|---|
| `-D_FORTIFY_SOURCE=3` | `memcpy`, `snprintf`, `read` и др. проверяют размер буфера, если он известен компилятору; переполнение — аварийная остановка, а не перезапись памяти |
| `-fstack-protector-strong` | канарейка на стеке функций с массивами: перезапись адреса возврата обнаруживается до `ret` |
| `-fstack-clash-protection` | стек растёт постранично с касанием: большой массив не «перепрыгнет» защитную страницу в кучу |
| `-fcf-protection=full` | метки IBT и теневой стек CET. На Comet Lake (i5-10500H) аппаратной поддержки CET нет, флаг безвреден и защитит на новых CPU |
| `-fPIE -pie` | программа грузится по случайному адресу (ASLR для кода) |
| `-Wl,-z,relro,-z,now` | таблица GOT только для чтения после загрузки: её нельзя переписать, чтобы перехватить вызов |
| `-Wl,-z,noexecstack` | стек не исполняемый |
| `-ftrivial-auto-var-init=zero` | неинициализированные локальные переменные — нули, а не остатки чужих данных |
| `-fno-strict-overflow`, `-fno-delete-null-pointer-checks` | компилятор не выбрасывает проверки, которые «по стандарту не нужны» |
| `-Wall -Wextra -Wformat=2 -Wshadow -Wvla -Werror` | любое предупреждение — ошибка сборки |

Проверить флаги готовой программы можно так (нужен `binutils`, например, в live-среде):
`readelf -lW /mnt/usr/local/bin/vh-wlfilter | grep -E 'GNU_RELRO|GNU_STACK'` и
`readelf -d … | grep BIND_NOW`.

## 5. Обновление после `git pull`

Программы обновляются вместе с репозиторием, но собрать их можно только там, где есть
компилятор, то есть в live-среде:

```sh
# [LIVE] загрузиться с флешки, затем
cryptsetup open /dev/nvme0n1p2 cryptroot
mount /dev/mapper/cryptroot /mnt
cd /путь/к/void-hardened && git pull
install/build-tools.sh /mnt
umount /mnt && cryptsetup close cryptroot
```

`build-tools.sh` заменяет и копии, которые уже поставили включённые модули
(`/usr/local/sbin/vh-deadman`, `/usr/local/bin/vh-open` и т. д.). Если обновился
`vh-limine-update`, после загрузки выполните `doas xbps-reconfigure -f linux6.18`.

## 6. Как проверено

`sh tests/c/run.sh` запускается на машине разработчика, нужен docker. Каждая проверка
идёт в одноразовом контейнере Void:

1. **Сборка** под x86_64 со всеми флагами и `-Werror`.
2. **`vh-seccomp`**: самопроверка (48 случаев во встроенном интерпретаторе BPF) и
   **побайтное** совпадение обоих фильтров с Python-эталоном.
3. **Дифференциальные тесты.** Одинаковый вход идёт в Python-эталон (берётся из истории
   git) и в C-версию, выход сравнивается байт в байт:
   - `vh-wlfilter`: 15 ручных сценариев. Среди них скрытые глобалы, привязка скрытого
     объекта, заголовки с управляющими и bidi-символами, деление fd по 28, ошибки размеров
     и строк, сообщения, разрезанные между пакетами;
   - `vh-limine-update`: 24 комбинации `KEEP`, наличия ключа и аргументов. Совпадают
     вывод, `limine.conf`, хэши BLAKE2b (в том числе файла больше 1 МБ) и итоговая ESP;
   - `vh-uki-verify`: синтетическая UKI (PE с ранним cpio и cpio в zstd); проверены
     `--init`, совпадение, подмена cmdline, `.uname` и initramfs;
   - `vh-open`: 18 случаев — типы файлов, симлинки, каталоги, `..`, справка. Совпадают
     аргументы `bwrap`, фильтр в memfd и цель дескриптора;
   - `vh-usb-udev`: поддельный sysfs, 9 устройств (BadUSB, свой и чужой ключ FIDO,
     встроенные камера и Bluetooth) при трёх настройках;
   - `vh-pkg`: настоящий xbps, пакет `fuse3`: SUID, udev 0666, `--ignore`, `scan`, `rm`,
     отказ. Отдельно — снятие capabilities (`iputils`).
4. **Фаззинг `vh-wlfilter`**: сотни случайных последовательностей сообщений через сборку с
   AddressSanitizer и UBSan. Любая ошибка памяти остановила бы прокси и дала бы различие.
5. **`pin-fetch`**: тот же PEM и отпечаток, что у эталона, на настоящих Quad9 (DoT 853) и
   Cloudflare (NTS-KE 4460); сервер с чужим именем отвергается.
6. **VM-стенд** (`tests/c/build.sh`, затем `python3 tests/vm/check.py ШАГ --repo`):
   настоящие демоны, Firefox через C-прокси, стирание ключа с дампом RAM
   ([00](00-prepare.md)).

## 7. Код на C и недоверенные данные

У C нет защиты памяти, как у Python: ошибка в разборе данных может стать уязвимостью. Три
программы читают данные, которые может подделать атакующий:

| Программа | Чьи данные | Что сделано |
|---|---|---|
| `vh-wlfilter` | сообщения Wayland от браузера (он мог быть взломан) | каждое поле читается после проверки длины; размер сообщения 8…4096 и кратен 4; строка — с проверкой длины до конца сообщения; номера объектов — в хэш-таблице без фиксированных массивов; ошибка рвёт только это соединение; фаззинг под ASan/UBSan |
| `vh-usb-udev` | дескрипторы USB-устройства (их пишет само устройство) | каждый дескриптор — с проверкой длины до конца буфера; путь устройства — только существующий, внутри `/sys/devices` |
| `vh-uki-verify` | секции PE и архивы cpio из UKI | смещения и размеры ограничены длиной файла; поля cpio — строго 8 hex-символов; управляющие символы в именах заменяются при записи эталона |

Остальные программы читают только файлы root, sysfs и ответы ядра.

## 8. Что изменилось в поведении

| Программа | Было (Python) | Стало (C) |
|---|---|---|
| `vh-deadman` | без MOR после `sysrq o` (выключение, асинхронно) сразу шёл `sysrq b` — машина, скорее всего, **перезагружалась**, и RAM оставалась под питанием | без MOR — только выключение (`sysrq o`) и ожидание |
| `vh-uki-verify` | скрытые файлы (`.имя`) в каталогах сборки не проверялись, симлинк — по содержимому цели | проверяются все файлы, симлинк — по цели ссылки. **Если эталоны уже записаны, перезапишите их:** `doas vh-keys mount && doas vh-uki-verify --init` |
| `vh-usb-udev` | путь, который `realpath` не нашёл, мог пройти проверку `/sys/devices` | только существующие пути внутри `/sys/devices` |
| `vh-acpid` | при конце потока событий устройства — бесконечный цикл | выход с ошибкой, runit перезапускает |
| `vh-pkg`, `vh-limine-update`, `vh-uki-verify` | `PATH` от вызывающего | `PATH=/usr/bin`: подмена программы через `PATH` невозможна |
| `vh-pkg` | — | `python3`, `perl`, `ruby`, `nodejs` помечаются как нежелательные (обходят `noexec`) |
| Справка (`-h`, неверные аргументы) | весь комментарий из начала файла | короткая строка использования; подробности — в этом руководстве |

## 9. Как читать исходники

Если вы учитесь системному программированию, читайте в таком порядке — от простого к
сложному:

1. `src/vh-seccomp.c` и `src/seccomp.c` — classic BPF: как фильтр решает, какой системный
   вызов разрешить; ассемблер с метками и интерпретатор для самопроверки.
2. `src/vh-acpid.c` — устройства ввода (`/dev/input/eventN`, `struct input_event`,
   `EVIOCGSW`), `poll()` с таймаутом без лишних пробуждений, запуск программы с понижением
   прав через `setpriv`.
3. `src/vh-usb-udev.c` — sysfs и авторизация USB, разбор дескрипторов.
4. `src/vh-limine-update.c` и `src/hash.c` — BLAKE2b и атомарная замена файлов
   (`.new` → `fsync` → `rename`).
5. `src/vh-wlfilter.c` — сокеты UNIX, передача дескрипторов (`SCM_RIGHTS`), `epoll`,
   обратное давление, протокол Wayland на уровне байтов.
6. `src/vh-deadman.c` — `ioctl` device-mapper, netlink-сообщения ядра (uevent), `mlockall`,
   `sysrq`.
