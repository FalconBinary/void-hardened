# 17. Инструменты системы на Zig

Свои программы системы написаны на Zig (каталог [`zig/`](../zig)): прокси Wayland, демоны
крышки и стирания ключа, обновление загрузчика, установка пакетов и другие. История:

- до коммита `a7665bd` — Python;
- до `39cf905` — C;
- с октября 2026 — Zig.

Пакетный менеджер thor с его политикой тоже на Zig ([18](18-thor.md)).

Эта глава объясняет:

- зачем был каждый переход;
- что они дали в цифрах;
- как программы собираются, обновляются и проверены;
- что изменилось в поведении.

## 1. Зачем

**Python → C: безопасность.** Интерпретатор с FFI обходит `noexec`: Python через `ctypes`
выделяет исполняемую память и запускает в ней машинный код, без файла и без `memfd`.
Монтирование `/home` и `/tmp` с `noexec` от этого не защищает ([05](05-system.md)). Пока
системным инструментам был нужен `python3`, его приходилось держать в системе. Теперь его
нет совсем:

- xbps не ставит его даже как зависимость (`ignorepkg=python3` в
  `/etc/xbps.d/20-vh-ignorepkg.conf`);
- thor отменяет транзакцию, если python3 в ней появится ([18](18-thor.md));
- `vh-audit` проверяет, что в системе нет ни интерпретаторов с FFI, ни компиляторов.

`apparmor` и `nftables` объявляют `python3` зависимостью, но только ради своих
Python-обвязок. `apparmor_parser`, `aa-status`, `aa-exec` и `nft` — программы на C, без
Python они работают. Не будут работать только `aa-logprof`, `aa-genprof` и
`aa-complain`/`aa-enforce`. Вместо двух последних: `apparmor_parser -r -C ПРОФИЛЬ` (режим
complain) и `apparmor_parser -r ПРОФИЛЬ` (режим из файла профиля).

**C → Zig: та же скорость, меньше способов ошибиться с памятью.** Три программы разбирают
данные, которые может подделать атакующий (раздел 7). В C каждую проверку длины пишет
человек, и одна забытая проверка — уязвимость. Zig в режиме ReleaseSafe оставляет в
программе проверки, которые срабатывают на этапе выполнения: выход за границы массива,
переполнение целого, `null`, недостижимый код. Ошибка останавливает программу, а не
портит память. Проверки, которые были в C, остались, а ReleaseSafe — дополнительная
страховка. Кроме того:

- **gcc больше не нужен ни для чего.** Инструменты, thor и сама libxbps собираются одним
  компилятором Zig (C-код — через `zig cc`), который скачивается в RAM live-среды и
  проверяется подписью ([02](02-bootstrap.md)).
- **Программы без библиотек — статические.** Десять из двенадцати не зависят от glibc
  системы: обновление glibc их не затрагивает, подменить им библиотеку через `ld.so`
  нельзя.
- **Одна сборка для разработчика и системы.** На Mac или любом Linux
  `zig build -Dtarget=x86_64-linux` собирает те же бинарники, что live-среда, без
  контейнеров и эмуляции.

## 2. Что где

| Программа | Место в системе | Кто запускает | Что делает |
|---|---|---|---|
| `vh-wlfilter` | `/usr/local/bin` | сеанс (exec-once mango) | фильтрующий прокси Wayland для песочниц ([08](08-desktop.md)) |
| `vh-seccomp` | `/usr/local/libexec/vh` | `browser-sandbox`, `vh-audit` | фильтр seccomp-BPF для bwrap ([08](08-desktop.md)) |
| `vh-acpid` | `/usr/local/sbin` | runit | крышка, кнопка питания, простой ([05](05-system.md)) |
| `vh-limine-update` | `/usr/local/sbin` | хук ядра | подпись UKI, `limine.conf` с хэшами ([03](03-boot.md)) |
| `vh-pkg` | `/usr/local/sbin` | админ | установка и удаление программ (обёртка над thor, [12](12-daily.md)) |
| `vh-deep-clean` | `/usr/local/sbin` | админ | очистка системы с резервом и проверкой ([12](12-daily.md)) |
| `vh-deadman` | модуль deadman | runit, стадия 3 | стирание ключа LUKS ([13](13-optional.md)) |
| `vh-uki-verify` | модуль sb-offline-keys | `vh-limine-update` | проверка входных данных UKI ([13](13-optional.md)) |
| `vh-open` | модуль viewers | пользователь | просмотр файлов в песочнице ([13](13-optional.md)) |
| `vh-usb-udev` | модуль usb-auth | udev | решение об авторизации USB ([13](13-optional.md)) |
| `pin-fetch` | модуль dns-pin | `enable` | корень цепочки TLS для пиннинга ([13](13-optional.md)) |
| `vh-hashpw` | `/root/vh/tools` | только VM-стенд | хэш пароля yescrypt |

Общий код:

- `zig/lib/vh.zig` — сообщения, файлы, конфиги `KEY=VALUE`, запуск программ без шелла;
- `zig/lib/hash.zig` — SHA-256 и BLAKE2b-512 из стандартной библиотеки Zig;
- `zig/lib/seccomp.zig` — генератор фильтров, общий для `vh-seccomp` и `vh-open`.

Внешние библиотеки есть только у `pin-fetch` (OpenSSL — TLS) и `vh-hashpw` (libxcrypt).

**Почему без `std.Io`.** Стандартная библиотека Zig до 1.0 меняется от релиза к релизу,
особенно новый интерфейс ввода-вывода `std.Io`. Поэтому `vh.zig` работает прямо через
системные вызовы Linux (`std.os.linux`): этот слой стабилен, а все места, которые зависят
от версии Zig, собраны в одном файле. Версия компилятора закреплена в `zig/ZIG_VERSION`
(0.17.0) — другой версией сборка не поддерживается.

Скрипты на `sh` (`vh-update`, `vh-audit`, `vh-suid-strip`, `vh-net`, `vh-usb`, модули)
остались на `sh`. Это «клей»: они вызывают thor, `sv` и `nft`, и время уходит на сами эти
программы. Переписывать их нет смысла: быстрее не станет, а читать и проверять будет
труднее.

## 3. Замеры

Одинаковый вход, родной arm64-контейнер Void на Apple M-серии. На i5-10500H всё медленнее
примерно вдвое, соотношение то же. Замер прокси — `tests/zig/bench_wlfilter.py`, поток
сообщений «кадр + ответ композитора».

| Что | Python | C | Zig |
|---|---|---|---|
| `vh-wlfilter`: CPU на сообщение Wayland | 0,69 мкс | 0,017 мкс | 0,019 мкс |
| `vh-wlfilter`: память в простое / после 27 млн сообщений | 11,4 МБ | 1,2 / 1,5 МБ | 0,5 / 1,0 МБ |
| `vh-seccomp`: запуск (при каждом запуске браузера) | 14 мс | 0,23 мс | < 0,3 мс |
| Размер одной программы (x86_64) | — | ≈ 50 КБ + glibc | ≈ 300 КБ, статическая |

**Как это выглядит на деле.** При прокрутке и видео браузер шлёт тысячи сообщений в
секунду. На C и на Zig это сотые доли процента одного ядра, разница между ними в пределах
погрешности. Статические программы больше по размеру (в них своя часть стандартной
библиотеки), зато в памяти занимают меньше: не загружается glibc. Скорость системы
(`tools/vh-bench`, сравнение с CachyOS — [15](15-cachyos.md)) определяют ядро, Mesa,
Firefox и mango, а не эти программы.

## 4. Сборка

```sh
cd zig && zig build -Dtarget=x86_64-linux --prefix КАТАЛОГ   # статические программы
zig build -Dtarget=native -Dlibc-tools=true …                 # плюс pin-fetch и vh-hashpw (нужны openssl-devel, libxcrypt-devel)
```

В установленной системе **нет компилятора** — намеренно: вредонос с правами пользователя
не соберёт на месте свой инструмент (thor запрещает `gcc`, `clang`, `zig`, `make`).
Поэтому программы собирает установщик — в RAM live-среды:

```sh
install/build-tools.sh /mnt     # Zig с ziglang.org (подпись minisign) в RAM, сборка, установка в /mnt
```

`10-install.sh` вызывает его сам после копирования файлов. После перезагрузки live-среды
от компилятора не остаётся следа.

**Защита программ:**

| Что | Что даёт |
|---|---|
| ReleaseSafe | проверки границ массивов, переполнения целых, `null`, `unreachable` остаются в программе: ошибка — аварийная остановка, а не перезапись памяти |
| статическая PIE (`-fPIE`, `pie = true`) | программа грузится по случайному адресу (ASLR для кода); без `ld.so` и библиотек системы |
| полный RELRO (`link_z_relro`, `link_z_lazy = false`) | таблицы указателей только для чтения после загрузки |
| `strip` | без отладочной информации (меньше размер; трассировка паники — без имён функций) |
| C-код (libxbps в thor) | те же флаги, что были у инструментов на C: `-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, `-fstack-clash-protection`, `-fcf-protection=full`, `-ftrivial-auto-var-init=zero` |

Канарейки стека и FORTIFY в Zig-коде не нужны: переполнение буфера ловят проверки границ
ReleaseSafe.

## 5. Обновление после `git pull`

Программы обновляются вместе с репозиторием, но собрать их можно только там, где есть
компилятор, то есть в live-среде:

```sh
# [LIVE] загрузиться с флешки, затем
cryptsetup open /dev/nvme0n1p2 cryptroot
mount /dev/mapper/cryptroot /mnt
cd /путь/к/void-hardened && git pull
install/build-tools.sh /mnt
install/build-thor.sh /mnt       # если менялся thor/; затем в системе doas xbps-install -Su thor
umount /mnt && cryptsetup close cryptroot
```

`build-tools.sh` заменяет и копии, которые уже поставили включённые модули
(`/usr/local/sbin/vh-deadman`, `/usr/local/bin/vh-open` и т. д.). Если обновился
`vh-limine-update`, после загрузки выполните `doas xbps-reconfigure -f linux6.18`.

## 6. Как проверено

`sh tests/zig/run.sh` запускается на машине разработчика, нужен docker. Zig собирает
программы на хосте, проверки идут в одноразовом контейнере Void родной архитектуры:

1. **Юнит-тесты** (`zig build tests`): парсеры, ассемблер BPF, категории путей, UTF-8,
   cpio, дескрипторы USB, классификация устройств ввода, uevent.
2. **Дифференциальные тесты против C-эталона.** Последняя C-версия берётся из истории git
   (коммит `39cf905`) и собирается gcc в контейнере. Одинаковый вход идёт в обе версии,
   выход сравнивается байт в байт:
   - `vh-seccomp`: оба фильтра побайтно и вывод самопроверки (48 случаев во встроенном
     интерпретаторе BPF);
   - `vh-wlfilter`: 15 ручных сценариев и 200 случайных (фаззинг). Среди них скрытые
     глобалы, привязка скрытого объекта, заголовки с управляющими и bidi-символами,
     деление fd по 28, ошибки размеров и строк, сообщения, разрезанные между пакетами.
     Любая паника ReleaseSafe дала бы различие;
   - `vh-limine-update`: 24 комбинации `KEEP`, наличия ключа и аргументов, включая хэш
     BLAKE2b файла больше 1 МБ;
   - `vh-uki-verify`: синтетическая UKI (PE с ранним cpio и cpio в zstd);
   - `vh-open`: 18 случаев, совпадают аргументы `bwrap`, фильтр в memfd и цель дескриптора;
   - `vh-usb-udev`: поддельный sysfs, 9 устройств при трёх настройках;
   - `vh-deadman`: режим `test`; размер `struct dm_ioctl` и номера ioctl сверены с
     заголовками ядра;
   - `pin-fetch`: тот же PEM и отпечаток на настоящем DoT-сервере 1.1.1.1:853, чужое имя
     отвергается;
   - `vh-hashpw`: хэш yescrypt подтверждает сама libcrypt.
3. **`vh-deep-clean` и `vh-pkg rm`**: 32 проверки на настоящем xbps (`clean_test.sh`): что
   удаляется, что остаётся, ловушки-симлинки, резерв и `restore`.
4. **VM-стенд** (`tests/zig/build.sh`, затем `python3 tests/vm/check.py ШАГ --repo`):
   настоящие демоны, Firefox через прокси, пересборка UKI, стирание ключа с дампом RAM
   ([00](00-prepare.md)).

## 7. Недоверенные данные

Три программы читают данные, которые может подделать атакующий:

| Программа | Чьи данные | Что сделано |
|---|---|---|
| `vh-wlfilter` | сообщения Wayland от браузера (он мог быть взломан) | каждое поле читается после проверки длины; размер сообщения 8…4096 и кратен 4; строка — с проверкой длины до конца сообщения; номера объектов — в хэш-таблице; ошибка рвёт только это соединение; фаззинг |
| `vh-usb-udev` | дескрипторы USB-устройства (их пишет само устройство) | каждый дескриптор — с проверкой длины до конца буфера; путь устройства — только существующий, внутри `/sys/devices` |
| `vh-uki-verify` | секции PE и архивы cpio из UKI | смещения и размеры ограничены длиной файла; поля cpio — строго 8 hex-символов; управляющие символы в именах заменяются при записи эталона |

Поверх ручных проверок — проверки границ ReleaseSafe. Остальные программы читают только
файлы root, sysfs и ответы ядра.

## 8. Что изменилось в поведении

| Программа | Было | Стало |
|---|---|---|
| `vh-pkg` | сам разбирал установленные файлы, спрашивал «Ставить всё равно?» о нежелательном пакете | обёртка над thor: обезвреживание — в libxbps при распаковке ([18](18-thor.md)); запрещённый пакет — отказ, разрешение — `thor allow ИМЯ`; `scan` только снимает вернувшиеся SUID (разбор делает thor) |
| `vh-deep-clean` | время резерва — местное | время резерва — UTC (без libc нет разбора часового пояса) |
| `vh-deep-clean` | — | не запускается, пока работает `thor` (как с `xbps-install`) |
| `vh-deadman` | статус `/run/vh/deadman` писался по симлинку | `O_NOFOLLOW` |

История перехода с Python на C — в git: `git show 39cf905:docs/17-zig-tools.md`.

## 9. Как читать исходники

Если вы учитесь системному программированию, читайте в таком порядке — от простого к
сложному:

1. `zig/lib/vh.zig` — системные вызовы без libc: `open`, `statx`, `getdents64`, `fork` и
   `execve`, `poll` по каналам; ошибки — через `errno` и `error.Sys`.
2. `zig/lib/seccomp.zig` и `zig/tools/vh-seccomp.zig` — classic BPF: как фильтр решает,
   какой системный вызов разрешить; ассемблер с метками и интерпретатор для самопроверки.
3. `zig/tools/vh-acpid.zig` — устройства ввода (`/dev/input/eventN`, `struct input_event`,
   `EVIOCGSW`), `poll()` с таймаутом без лишних пробуждений, запуск программы с понижением
   прав через `setpriv`.
4. `zig/tools/vh-usb-udev.zig` — sysfs и авторизация USB, разбор дескрипторов.
5. `zig/tools/vh-limine-update.zig` — BLAKE2b и атомарная замена файлов (`.new` → `fsync`
   → `rename`).
6. `zig/tools/vh-wlfilter.zig` — сокеты UNIX, передача дескрипторов (`SCM_RIGHTS`),
   `epoll`, обратное давление, пул буферов, протокол Wayland на уровне байтов.
7. `zig/tools/vh-deadman.zig` — `ioctl` device-mapper (структура `dm_ioctl` описана
   вручную и сверена с ядром), netlink-сообщения ядра (uevent), `mlockall`, `sysrq`.
8. `thor/policy/policy.zig` — Zig-код внутри C-библиотеки: функции с C ABI (`export fn`),
   которые вызывает libxbps.
