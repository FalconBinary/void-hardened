# 18. thor — пакетный менеджер void-hardened

**thor** — это xbps 0.60.7 из Void с двумя дополнениями:

1. **Политика безопасности внутри libxbps.** Опасное из пакетов обезвреживается ещё при
   распаковке, а не после установки. Политика вшита в саму библиотеку, поэтому действует во
   всех программах `xbps-*`: обойти её прямым вызовом `xbps-install` нельзя.
2. **Команда `thor`.** Пакеты качаются параллельно, есть выбор быстрого зеркала и
   переход на запасное при сбое.

Пакет `thor` заменяет пакеты `xbps` и `libxbps`. Все команды `xbps-*` остаются на месте и
работают как раньше: их вызывают хуки ядра, `vkpurge`, dracut, наши скрипты и вы сами.

## 1. Зачем

Раньше защита при установке программ была «снаружи» xbps: `vh-pkg` ставил пакет, а
потом снимал SUID, маскировал правила udev и удалял хуки. Из этого следовали три слабых
места:

- **окно между распаковкой и проверкой**: файл с SUID какое-то время лежал на диске;
- **обновления не проверялись**: `xbps-install -u` мог тихо притянуть новую зависимость из
  чёрного списка (например, polkit);
- **обход**: `xbps-install` напрямую, мимо `vh-pkg`, ставил всё без проверок.

Кроме того, xbps качает пакеты **строго по одному**. Время установки системы и
обновлений уходит на ожидание сети (задержка каждого запроса), а не на саму скорость
канала.

## 2. Что делает политика

| Что в пакете | Что делает thor | Когда |
|---|---|---|
| SUID/SGID у файла | бит снимается **до записи на диск**; разрешены только `doas` и `unix_chkpwd` | распаковка |
| SUID или capability, которые поставил скрипт INSTALL (`chmod u+s`, `setcap`) | снимаются; разрешена только `cap_syslog` у `nanoklogd` (журнал ядра, socklog) | сразу после настройки пакета |
| хук `/etc/kernel.d/…` (исполняется от root при каждой сборке UKI) | не распаковывается | распаковка |
| модуль dracut `/usr/lib/dracut/modules.d/…` (попал бы в initramfs) | не распаковывается | распаковка |
| скрипт входа `/etc/profile.d/*.sh`, `/etc/bash/bashrc.d/*` (исполнялся бы в каждом шелле) | не распаковывается | распаковка |
| `sysctl.d` пакета (99-* перекрыл бы `30-vh-hardening`) | маскируется одноимённым файлом в `/etc/sysctl.d` | распаковка |
| правило udev с `MODE="0666"`/`0777` (устройство для всех) | маскируется в `/etc/udev/rules.d` (файл в `/etc` — удаляется) | сразу после распаковки файла |
| пакет из чёрного списка (компиляторы, интерпретаторы, polkit, cups, sshd, Xwayland…) | **транзакция отменяется** — и при установке, и при обновлении, и если это зависимость | подготовка транзакции |
| сервис runit, D-Bus, автозапуск, cron, modprobe.d | только сообщение (здесь они сами не запускаются) | после установки |

Чёрный список (45 пакетов и 2 префикса) — в [`thor/policy/rules.zig`](../thor/policy/rules.zig),
у каждого пакета указана причина. Посмотреть всё сразу: `thor policy`.

**Базовый список.** Хуки ядра, модули dracut и правила udev есть и в пакетах самой
системы: `dracut` ставит свой хук `20-dracut`, `eudev` — правила с `MODE="0666"` для
`/dev/null`. Их трогать нельзя. Поэтому во время установки (`10-install.sh`) политика
работает в режиме **learn**: такие файлы базовой системы не обезвреживаются, а
записываются в `/etc/thor/baseline`. В конце установки включается **enforce**. SUID,
capabilities и чёрный список действуют уже во время установки: система с самого начала
собирается в том виде, который проверяет `vh-audit`.

Всё, что политика сделала, пишется в stderr (`thor: …`) и в журнал `/var/log/thor.log`.

### Исключения

```sh
doas thor allow cups                     # разрешить пакет из чёрного списка (спросит y/N, покажет причину)
doas thor keep /usr/bin/fusermount3      # SUID этого файла не снимать
doas thor keep /usr/lib/dracut/modules.d/70tpm2-totp/   # модуль dracut — распаковывать
```

Исключения хранятся в `/etc/thor/allow.conf` и `/etc/thor/keep.conf` и действуют и при
обновлениях. После `thor keep` файл, который уже был пропущен, появится только при
переустановке пакета: `doas xbps-install -f ПАКЕТ`. Модуль `optional/tpm2-totp` делает
`thor keep` для своего модуля dracut сам.

### Что политика не закрывает

- **root.** Root может отредактировать `/etc/thor/*` или поставить пакет с флешки.
  Политика защищает от ошибки и от пакета с сюрпризом, а не от взломанного root.
- **Само содержимое программ.** thor не проверяет, что делает программа, только
  установочные «точки входа»: SUID, хуки, правила, автозапуск.
- **Окно для capabilities.** Capabilities ставят только скрипты INSTALL: libarchive в xbps
  не распаковывает xattr. Поэтому они снимаются сразу после скрипта, а не до записи. Между
  ними — доли секунды, пока запущен root-процесс xbps.

## 3. Параллельная загрузка

```sh
doas thor install firefox mpv     # как xbps-install -S, плюс параллельная загрузка
doas thor update                  # как xbps-install -Su
doas thor fetch -u                # только скачать (и проверить подписи) — например, перед офлайн-подписью
doas thor remove mpv              # = xbps-remove
thor search pdf                   # = xbps-query -Rs
```

Как это устроено:

1. thor синхронизирует репозитории (`xbps-install -S`) и спрашивает у `xbps-install -n` план транзакции: какие пакеты откуда ставить.
2. Пакеты, которых нет в кэше, качают **N процессов-воркеров** (по умолчанию 4). Каждый
   использует штатный загрузчик libxbps (`xbps_fetch_file_dest`): тот же TLS, прокси,
   докачка `.part` и keep-alive внутри воркера. Новый сетевой код не писался.
3. Затем запускается обычный `xbps-install`. Он находит пакеты в кэше и **сам проверяет
   подпись RSA каждого** (тем же ключом репозитория Void). Подменённый пакет или пакет с
   плохого зеркала не пройдёт: это проверено тестом.

**Без нагрузки на железо.** Воркеры работают с пониженным приоритетом процессора
(`nice 10`) и диска (ioprio best-effort 7). Пакеты пишутся на диск потоком, поэтому память
не растёт с числом воркеров. Распаковка идёт по одному пакету, как в xbps. Ограничить
скорость: `ratelimit=` в `/etc/thor/thor.conf`.

**Замер** (192 пакета, 110 МБ, настоящее зеркало Void, пустой кэш):

| | время |
|---|---|
| `xbps-install -D` (по одному) | 68–85 с |
| `thor fetch` (4 потока) | 31–36 с |

Выигрыш больше всего на многих мелких пакетах (установка системы, большие обновления):
там время уходит на задержку сети, а не на объём данных.

### Зеркала

```sh
doas thor mirror            # замер: задержка до 24 HTTPS-зеркал, скорость с ближайших
doas thor mirror --write    # лучшее — в /etc/xbps.d/*.conf, 3 запасных — в /etc/thor/thor.conf
```

Если основное зеркало не отдаёт пакет (нет файла, 5xx, обрыв), воркер пробует запасные
зеркала по очереди с тем же путём. Подпись проверяется тем же ключом, поэтому запасное
зеркало подменить пакет не может. В строгом режиме сети (`optional/strict-net`) `vh-net
xbps` открывает и запасные зеркала. Сам `thor mirror` в этом режиме зеркала не увидит —
запускайте его до включения модуля или при открытой сети.

### Настройки — `/etc/thor/thor.conf`

```ini
parallel=4                 # воркеров загрузки (1–8); на один запуск: thor install -j 2 …
ratelimit=0                # КБ/с на всю загрузку, 0 — без ограничения
mirror-fallback=https://repo-fi.voidlinux.org
```

## 4. Как устроено

```
thor/
  UPSTREAM                        версия xbps, URL и sha256 архива (= шаблон Void)
  patches/0001-thor-policy-hooks.patch   ~100 строк C: вызовы политики в libxbps
  policy/policy.zig               политика (компилируется в thor_policy.o, линкуется в libxbps)
  policy/rules.zig                чёрный список и категории путей
  src/thor.zig                    команда thor
  build.sh                        сборка: xbps + патч + политика через «zig cc»
  package.sh                      пакет thor и индекс локального репозитория
```

**Патч к xbps минимальный.** Он вызывает политику в четырёх местах и ничего больше не
меняет:

- в распаковке — до записи каждого файла и сразу после;
- в подготовке транзакции — проверка пакетов;
- в завершении транзакции — разбор файлов после скриптов.

Проверка подписей, транзакции, pkgdb и распаковка — код upstream.

**Сборка без gcc.** C-код xbps собирается через `zig cc` (это clang внутри Zig) с теми же
флагами защиты, что были у инструментов на C ([17](17-zig-tools.md)). Программы получают
`rpath $ORIGIN/../lib`: в live-среде они берут libxbps с политикой из своего каталога, а не
штатную `/usr/lib/libxbps.so.6` флешки.

**Локальный репозиторий.** Пакет лежит в `/var/lib/thor/repo` (`/etc/xbps.d/01-thor.conf`).
Подписывать его не нужно: xbps сверяет локальный пакет с sha256 из индекса, а писать в
`/var/lib/thor` может только root. Обычный xbps из репозитория Void не поставится:
`ignorepkg=xbps` и запрет в чёрном списке — иначе политика пропала бы.

## 5. Установка и обновление thor

При установке системы ничего делать не нужно: `10-install.sh` сам собирает thor в RAM
live-среды (`install/build-thor.sh`) и ставит через него систему.

**Новый xbps в Void** (`vh-update` напишет «пересоберите thor»), или вы обновили
репозиторий void-hardened. Всё делается с флешки, как обновление инструментов:

```sh
# [LIVE] загрузиться с флешки, затем
cryptsetup open /dev/nvme0n1p2 cryptroot
mount /dev/mapper/cryptroot /mnt
cd /путь/к/void-hardened && git pull          # новая версия в thor/UPSTREAM — после ревью патча
install/build-thor.sh /mnt                     # пакет — в /mnt/var/lib/thor/repo
umount /mnt && cryptsetup close cryptroot
# после загрузки системы
doas xbps-install -Su thor
```

При новой версии xbps upstream сначала обновите `thor/UPSTREAM`: версию и sha256 из
шаблона Void (`void-packages/srcpkgs/xbps/template`). Затем проверьте, что патч
накладывается: `tests/thor/run.sh`.

**Перевод уже установленной системы на thor** (установка до появления thor):

```sh
# [LIVE] собрать пакет в систему: install/build-thor.sh /mnt (как выше), затем в системе:
doas sh -c 'printf "mode=enforce\n" > /etc/thor/policy.conf'
doas xbps-install -Sy thor        # заменяет xbps и libxbps
doas thor baseline                # базовый список — из уже установленных пакетов
doas vh-audit                     # раздел «SUID…»: thor установлен, политика enforce
```

## 6. Как проверено

`sh tests/thor/run.sh` запускается на машине разработчика (нужен docker): родной
контейнер Void, без эмуляции.

1. **Политика** (`policy_test.sh`, 32 проверки): тестовые пакеты с SUID, SGID, хуком ядра,
   модулем dracut, profile.d, sysctl.d, udev 0666 и 0777, сервисом runit, INSTALL-скриптом
   с `chmod u+s` и `setcap`. Проверены:
   - режимы learn и enforce;
   - keep;
   - **обновление**: файл с тем же хэшем xbps не перераспаковывает, а делает `chmod` по
     режиму из пакета — SUID не возвращается;
   - чёрный список и запрещённая зависимость (в том числе в `-n`);
   - allow.
2. **Загрузка** (`fetch_test.sh`): два HTTP-зеркала с подписанным тестовым репозиторием;
   у основного нет пакетов — всё приходит с запасного. Подменённый пакет (подпись от
   настоящего) не ставится. `thor fetch`, `-j 1`, кэш. `keep`, `allow`, `baseline`, `policy`.
3. **Пакет** (`package_test.sh`): thor ставится штатным xbps поверх настоящей системы
   Void и заменяет `xbps` и `libxbps`. Проверены:
   - xbps не требует обновить сам себя по кругу;
   - зависимость на `xbps` удовлетворена;
   - `xbps-pkgdb`;
   - установка из официального репозитория;
   - SUID у `fusermount3` снят.
4. **vh-pkg поверх thor** (`vhpkg_test.sh`).
5. **Путь установщика** (`live_test.sh`, отдельно: `docker run … sh tests/thor/live_test.sh`):
   - `build-thor.sh` в live-среде: Zig по подписи, xbps по контрольной сумме, пакет;
   - установка в пустой корень через thor в режиме learn: базовый список, SUID только у
     doas, `cap_syslog` у nanoklogd;
   - `build-tools.sh`;
   - режим enforce: модуль dracut нового пакета не распаковывается.
6. **VM-стенд**: шаг `thor` в `tests/vm/check.py`:
   - перевод установленной системы на thor;
   - установка через thor;
   - пересборка UKI;
   - `vh-audit` без FAIL;
   - перезагрузка.
